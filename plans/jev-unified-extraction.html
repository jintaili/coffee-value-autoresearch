Implementation plan · 21 September 2026

One JEV extraction contract for training and serving

Replace the two semantic extraction paths with a shared, versioned question catalog. Retrain the rating and price predictors, then demonstrate prediction gains and faster appraisals with separate, reproducible benchmarks.

Scope: coffee-grader and the local coffee-value-app companion repository. The training experiment and a small extraction-call timing pilot are complete; see the combined results report. Serving integration and a full appraisal benchmark remain future work.

Recommended decisions

Unify semantic extraction

Use the same JEV questions, state construction rules, probability encoding, and model version for historical reviews and product pages. Keep source-specific readers thin.

Measure both objectives

Prediction quality and serving latency are separate gates. Faster extraction does not establish better ratings; stronger review-validation scores do not establish faster product-page appraisals.

  • Implement one A+B extractor and compare three configurations: the incumbent, the existing architecture with JEV features, and a JEV-only predictor. Preserve the research winner as a comparison. Further feature ablations and architecture search are optional follow-ups.
  • Test a semantic-feature-only model early. It offers the clearest path to eliminating generative text extraction. Retain TF-IDF or embeddings only when their measured benefit warrants their serving cost.
  • Keep HTML parsing, candidate construction, unit conversion, FX/CPI normalization, and exact copying in code. These operations remain useful even when JEV owns semantic interpretation.
  • Do not add a routine JEV verification pass. Each field's missing/conflicting outcomes, distributions, and deterministic validation handle uncertainty within extraction.
  • Preserve existing display functionality and product-variant behavior. Benchmark the complete response the user receives, including any remaining display extraction or fallback.

Performance improvements are hypotheses until measured. If the experiments fail a gate, report the result and retain the incumbent for that component.

Keep the first pass small. A to E are tags in one question catalog, not separate pipelines. Initially implement only A+B, cache their answers once, and reuse the existing training code. No experiment framework or autonomous feature-discovery system is required. Complete training comparisons first; serving integration and production benchmarks follow.

Feature and commerce evidence stay separate

The shared feature state excludes ratings, reviewer component scores, listed prices, price-derived values, and explicit score/price quotations. Enforce this while building the state; a prompt telling JEV to ignore fields is insufficient isolation. Retain legitimate numbers such as altitude or fermentation hours. Audit difficult cases and retain raw source snapshots outside the model state.

Package grams remains an allowed input for price and stays excluded from rating. Commerce selection receives prices and units through a separate request when needed. It can run concurrently with feature extraction. Where embedded product data already identifies the correct variant, deterministic code avoids that request entirely.

All independent feature questions run in one JEV request when request limits permit. A commerce or display question must not depend on an answer from that same request. Construct candidate variants first and select a whole offer record containing price, currency, size, purchase type, and source IDs. This avoids selecting a price from one variant and a size from another.

Preserve exact data and existing behavior

  • Preserve URL-selected variants and the current default-size policy. Support one-time versus subscription prices, bundles, availability, and non-coffee pages.
  • Copy coffee names, producer names, raw process terms, and display text from metadata or candidate spans. JEV selects from supplied options; it does not generate arbitrary strings through Choice.
  • Include none in candidate selection. Measure candidate coverage separately from JEV selection accuracy. Missing candidates require an adapter fix or explicit fallback.
  • For a hybrid predictor requiring text, select sensory and producer source blocks, then copy their contents. Benchmark this extra work. A semantic-only predictor avoids that dependency.
  • Keep ordinary validation for units, positive package size, supported currencies, valid candidate IDs, and feature dimensions. Do not substitute a second model call for arithmetic.

Typed questions and grouped evaluation follow the TypeSafe API. Source selection follows the candidate extraction cookbook.

Start with the agreed Choice templates. Each field's instructions name the target, permitted evidence, definition, exclusions, and boundary examples. Question IDs alone carry no meaning for the model.

Shared evidence rule: judge statements about this lot, accept clear paraphrases and listed aliases, exclude background and other products, and infer nothing from price, reputation, or origin stereotypes. Repetition and promotional emphasis do not increase a sensory degree. Conflicting means incompatible source claims, not ordinary model uncertainty.

Store the full answer distributions even if the display uses a single label. A service failure must never become a valid not_stated answer. Backfills checkpoint completed rows and retry failed rows within a bounded policy.

Pin an explicit model version after the pilot. Current docs list jev-1.13.0; reconfirm at implementation time. A contract change or model upgrade requires a new cache namespace, evaluation, and compatible artifacts. Model documentation.

On matched data, compare predictions from review evidence and page evidence against the independent rating, and measure feature agreement. Agreement alone is insufficient: consistently wrong features can agree. For price, align currency, date normalization, package variant, and purchase type before comparing. A page's own asking price is a market-price label, not independent proof of fair value.

Measure classification precision/recall, macro scores over evidence states, probability quality where labels permit it, abstention/coverage, and candidate coverage. Report these by language and source type. Do not give the model credit simply for returning not_stated on most rare fields.

Inspect source prose for explicit ratings and prices after named columns are removed. Run a facts-only versus review-text ablation to expose dependence on evaluator language. Shared extraction cannot eliminate the difference between promotional descriptions and blind assessments.

Optional follow-ups, driven by the results

  • Compare hard labels with probabilities or remove A/B subgroups using the cached answers when attribution would help. These are column-selection experiments, not new extraction pipelines.
  • Add C or D only if residual errors suggest production details or specific lot claims would help. Extract only the new questions and preserve the original run.
  • Try shallow boosting only if the linear models appear limited by interactions. Reuse the same frozen features.
  • Defer E, the large annotation program, matched-page collection, serving timing instrumentation, and production rollout until the training result establishes a useful direction. Retain a small evidence audit and existing fixed evaluation rows from day one.

When a bounded autoresearch run is worthwhile

Use it only after the extraction contract is stable and the ablations reveal useful signal or systematic residuals. Start with at most 12 focused trials across both predictors, and stop after four consecutive trials fail to improve the predeclared development objective. Broader search is a later decision supported by measured gains, not the default migration step.

Model search reuses cached features. A feature-discovery round is a separate, budgeted experiment: propose a small group from development-only errors, audit its rubric, extract it, then evaluate its incremental value. Keep a final test set inaccessible to both the proposer and model selection. This adapts the TypeSafe feature-discovery approach to this deployment problem.

Update the existing autoresearch programs before execution. Their bans on LLM extraction and edits to the shared extractor describe the previous milestone. This migration intentionally changes that contract while preserving split IDs, target definitions, and append-only result history. Do not delete discarded experiment records or unrelated working-tree changes.

Metrics and uncertainty

  • Rating selection remains pairwise concordance. Also report MAE, RMSE, Spearman, within-one/two accuracy, calibration, rating-bucket bias, and train/validation gap.
  • Price selection remains the existing RMSLE implementation and real USD/100g target. Report p90/median error, low/high-decile RMSLE, bias, and top-decile sensitivity to the extreme outlier.
  • Use paired bootstrap intervals over independent product/lot groups where available. Recompute concordance in each resample; do not treat the many pairwise comparisons as independent observations.
  • Show development results and the frozen final evaluation separately. Confidence intervals on a repeatedly tuned validation set do not remove selection bias.
  • Reassess the app's displayed prediction intervals using development calibration residuals and evaluate their coverage on held-out data. Do not reuse the current fixed interval constants without checking them, or derive prediction intervals directly from JEV confidence.

Optimization order

  1. Replace the generative semantic extractor with grouped JEV questions. Reuse the connection/client and validate complete answers.
  2. Use embedded product data for exact fields and candidate generation. Keep feature and commerce calls concurrent when both are necessary.
  3. Remove low-value questions and unnecessary source text only after measuring their effect on extraction quality. Preserve relevant middle-of-page content rather than rely on blind head/tail truncation.
  4. Prefer a compact JEV-only regressor if it meets quality gates. If embeddings remain useful, measure their actual loading and inference cost.
  5. Evaluate country-resolution caching or policy changes separately. The current serial web lookup may dominate slow requests, but removing it changes available evidence and must not be credited to JEV alone.

Default to one feature request and, only when needed, a separate concurrent commerce request. Large candidate sets or dependent source selection may need another stage; count these explicitly. No blanket verifier. A rare fallback may recover missing display/commerce information, but if it changes core feature semantics, route through the full compatible legacy model bundle instead of mixing contracts.

Before the full benchmark/backfill, run a 30 to 50 item pilot to estimate input tokens, success rate, latency, and total cost. Publish projected and actual costs using the applicable provider rates. Cap concurrency, attempts, and total run spend in configuration. Use fresh provider latency measurements rather than assume JEV is faster because its response is shorter.

Tests that materially reduce migration risk

  • Golden cached-answer tests proving both consumers emit identical feature names, order, values, and predictions within an explicit numeric tolerance.
  • Contract mismatch tests that reject wrong catalog/model/encoder versions, incomplete answers, invalid distributions, and incompatible feature dimensions.
  • Input-state tests proving score/price fields cannot reach feature extraction, while valid altitude/processing numbers survive.
  • Snapshot integration tests for selected variants, subscriptions, multi-bag totals, currencies, unknown fields, conflicting evidence, non-coffee pages, long text, and provider timeouts.
  • Semantic examples such as honey notes, Java ambiguity, and espresso suggestions belong in the live evaluation set. Mocking the intended answer is not evidence that JEV handles them.

Ordinary CI replays recorded answers and makes no paid calls. A separate integration evaluation exercises the pinned provider. Repeated live extraction of a small sample measures output stability; version pinning alone does not guarantee bit-identical provider results.
